# 管理员/用户工作台分流与邮箱注册执行计划书

前置说明书：[编写与执行规范](../../../执行计划书编写与执行规范.md) · [项目整体说明书](../../../项目整体说明书.md) · [需求](../../../项目需求说明书.md) · [数据库](../../../数据库设计说明书.md)。

日期：2026-09-22。版本：0.1。确认状态：用户于 2026-09-22 确认并授权编码；真实邮件与页面终点验收仍不在本轮授权范围。

## 1. 当前状态

Vue 端只有一套 `Layout` 和 `/index`，首页文案、快捷入口均面向管理员；动态菜单虽由后端角色过滤，但登录成功仍一律进入该管理员首页。平台开发者角色（`developer`，role_id=2）及制作、我的角色、我的应用菜单已存在。

前端已有 `register.vue` 和 `/auth/register` 调用，但登录页把入口固定关闭；后端注册只接收账号和密码，`sys.account.registerUser` 默认关闭，且未写入平台要求的邮箱与验证状态。`p_email_token`、邮箱唯一键和邮箱登录查询已存在，但邮件发送与邮箱验证流程未实现。

## 2. 目标与边界

同一 Vue 应用、同一登录体系内提供一套后台工作台：管理员和普通开发者都进入 `/index` 与既有后台 Layout；菜单和首页快捷入口按后端返回的权限动态显示，后端既有菜单与接口授权仍是唯一权限边界。

补齐普通开发者的邮箱注册与验证码验证：验证成功才创建可登录账号并绑定 `developer` 角色。管理员只能由既有受控账号管理流程授予，注册接口绝不接受角色、菜单、用户状态或账号 ID。

不拆分为两个前端工程，不改现有业务接口、资产/应用所有权规则，也不在本次做用户工作台的视觉重设计、密码重置或真实邮件服务开通。

## 3. 已确认决策

| 决策 | 结果 |
|---|---|
| 前端形态 | 复用一个前端部署和后台 Layout；所有账号进入同一工作台，菜单按权限变化。 |
| 管理员识别 | 仅以后端 `getInfo` 返回的 `admin` 角色识别，不能由前端路由参数或用户资料决定。 |
| 普通用户身份 | 自助注册成功后仅拥有既有 `developer` 角色。 |
| 注册准入 | 账号、邮箱、密码和图形验证码；邮箱验证码验证成功后才能创建并登录。 |
| 邮件通道 | 使用标准 SMTP 配置；主机、端口、账号、密码和发件人仅从被 Git 忽略、由 system 自动导入的 `application-local.yml` 读取，禁止写入仓库或 Nacos。 |

## 4. 完整流程与契约

1. 未登录者打开 `/register`，填写账号、邮箱和密码并完成图形验证码；“发送邮箱验证码”调用 `POST /auth/register/code`，网关也对该路径执行图形验证码校验。system 在 `p_email_token` 写入 `VERIFY_EMAIL` 的随机六码摘要（15 分钟有效、同邮箱 60 秒重发间隔、连续 5 次错误即失效），通过 SMTP 发送明文验证码；不记录明文验证码或 SMTP 凭证。
2. 提交 `POST /auth/register`，请求为 `{ username, email, password, emailCode, captchaCode, uuid }`。auth 仅做公网 HTTP、验证码和输入边界，转发至 system 的受保护内部注册服务；system 在同一事务中锁定并原子消费有效令牌、规范化邮箱、检查账号和邮箱唯一性、写入 `sys_user`（`email_verified_at` 为当前 UTC 时间）并只关联 role_id=2。失败不得创建账号或赋予角色。
3. 已验证的新用户用账号或邮箱登录；首次 `getInfo` 后统一进入 `/index`。带 `redirect` 的登录仅在目标属于已装配路由时保留，否则回到工作台。
4. `/index` 与动态菜单统一使用既有后台 `Layout`；管理员和开发者的菜单均来自 `/system/menu/getRouters` 的角色结果。权限不足的菜单和接口仍由后端拒绝，不能把“隐藏”当授权。

新增公开接口仅为 `POST /auth/register/code` 和已扩展字段的 `POST /auth/register`；成功响应沿用现有 AjaxResult。验证码发送、账号/邮箱已存在、验证码过期/错误、SMTP 配置缺失或投递失败均返回可展示的业务失败，不泄露令牌、密码或邮件配置。将 `sys.account.registerUser` 以迁移设为 `true`，保留该开关作为部署侧紧急关闭点。

## 5. 实施切片、验证与验收

| 切片 | 改动与退出条件 |
|---|---|
| C-A 工作台入口 | 统一使用后台 Layout 和 `/index`；权限存储按后端动态菜单装配同一布局，登录、根路由和过期旧地址均回到统一工作台。保留现有后台页面和菜单数据。 |
| C-B 邮箱注册 | 扩展 auth/system 内部契约与注册 DTO；复用 `p_email_token`、`sys_user` 邮箱唯一键和 developer 角色，实现 SMTP 验证码发送、原子验证消费及注册；新增迁移开启注册开关。 |
| C-C 文档与验证 | 更新本计划执行记录及项目整体说明书的计划入口和状态；添加聚焦的后端测试，覆盖验证码不能复用/过期、邮箱或账号冲突不建用户、成功后只授予 developer、未具备 admin 不进入管理工作台。运行 auth/system 受影响模块的离线测试或编译、Vue `npm run typecheck`、`git diff --check`。 |

用户终点验收：以一个管理员和一个新邮箱为普通用户完成注册，确认邮件验证码、账号/邮箱登录、管理员进入管理工作台、普通用户进入用户工作台、普通用户没有管理菜单且管理接口为 403；SMTP 配置和真实收件箱由用户提供并验收。代理默认不启动服务、不执行迁移、不发送真实邮件或登录浏览器。
