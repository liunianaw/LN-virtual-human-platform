### 2.1 服务职责映射

| 文档中的逻辑服务 | 实际承载模块 | 第一阶段职责 |
|---|---|---|
| gateway | RuoYi-Cloud/ruoyi-gateway | 后台与业务路由、WSS、凭证分类和基础访问校验 |
| auth-service | RuoYi-Cloud/ruoyi-auth | 后台邮箱登录/退出、登录状态和调试授权来源失效 |
| platform-service | RuoYi-Cloud/ruoyi-modules/ruoyi-system | 账号角色菜单、文件、Avatar/Voice、制作任务、官方服务、额度、最小应用配置 |
| session-service | RuoYi-Cloud/ruoyi-modules/ruoyi-session | 最小纯播报调试Session、短期授权、分段TTS、音频读取、停止与必要清理 |
| media-service | ruoyi-media | 生成API调用、CPU素材加工、结果回传、Worker恢复 |

platform-service 是职责名称，不再另建同名工程；ruoyi-system 就是平台业务服务。ruoyi-media 是一个 Python 项目，HTTP 与 Worker 分进程启动，不参加 Maven 编译。开发者转接示例不计为平台第六个逻辑服务。

### 2.2 模块内部组织和复用

- Java父工程入口固定为RuoYi-Cloud/pom.xml；后台入口固定为RuoYi-Cloud-Vue3/package.json。共用前端工作区配置可作为根文件补充，不迁移或复制后台到另一个一级目录。
- ruoyi-media/src/ruoyi_media内分api、worker、providers、media包；avatar-sdk/src内按连接、图集、动作、音频组织；各项目保留tests。examples/integration-demo内区分frontend/backend。RuoYi-Cloud/docker里的编排显式使用兄弟工程路径，不假定所有组件在Java目录内。

- 既有 Java 类、包名、Mapper 和模块依赖优先沿用。资产、制作任务、声音等新增业务在 ruoyi-system 内按领域分包，不新建一套后台账号、菜单或公共工具体系。
- ruoyi-api 放服务间接口和传输 DTO；新增业务不共享另一服务的 Mapper、持久化实体或数据库写权限。若依原有接口耦合的具体调整列入编码前裁剪/改造清单。
- RuoYi-Cloud-Vue3/src 沿用若依 Vue3 登录、布局、路由、菜单、权限指令与组件；资产、任务、预览、Voice和纯播报调试页面沿原有前端组织添加。原后台接口与新平台API的响应格式使用各自适配层。
- avatar-sdk 为独立 TS 包，管理后台也使用该包播放正式资产。第一阶段交付图集加载、动作与音频同步、停止和最小授权连接；不把Vue后台组件打入SDK。前端包用工作区引用和锁文件，validation保持其已有独立验证环境。
- 若依在现有根目录工程内直接改造，upstream中的其他开源项目保留作对照。复用代码记录来源提交、许可证与修改；不复制依赖缓存、模型权重、试验输出或本地凭证到正式工程。

### 2.3 迁移与配置位置

| 内容 | 目标位置与规则 |
|---|---|
| 平台库迁移 | RuoYi-Cloud/ruoyi-modules/ruoyi-system/src/main/resources/db/migration/ |
| 会话库迁移 | RuoYi-Cloud/ruoyi-modules/ruoyi-session/src/main/resources/db/migration/ |

每库只有一条受版本控制的迁移历史。正常启动执行或校验自身迁移，已应用版本不重跑、不事后改写；业务模块到达其开发步骤时追加新迁移，不要求骨架阶段一次创建48张表。第一阶段结束前，实际用到的表、外键、索引、初始化数据和清理记录必须完整落地。

## 4. 初始化及实现顺序

| 顺序 | 工作 | 本步可检查的产出 |
|---|---|---|
| 0 | 若依模块裁剪/改造 | 已执行：gateway/auth/system/job默认，gen/monitor按需；一级目录和组织兼容表保留 |
| 1 | 在现有RuoYi-Cloud和RuoYi-Cloud-Vue3内建立工程基线 | 保留原组织，核对上游提交、依赖可解析、前后端基础构建；记录必要版本调整，建立配置模板与检查入口 |
| 2 | 准备运行基础设施与配置 | MySQL、Redis、Nacos就绪；RabbitMQ在任务链开始前就绪；建立独立业务库与账号，配置能由本地和部署入口提供 |
| 3 | 建立两库Flyway基线与最小账号数据 | 若依系统表、必要项目改造与当前所需表有版本记录；管理员初始化由明确配置执行，种子数据不含共享默认密码 |
| 4 | 跑通若依后台和所有计划服务的基础入口 | system/session各自迁移并启动，再联通auth/gateway；media API与Worker基础健康就绪；Vue邮箱登录、退出、角色菜单、接口权限可验证，完成M1 |
| 5 | 文件、官方生成配置、任务与额度基础 | 参考图入云存储；任务、预占、Outbox与领取租约可追踪；重复提交不创建重复制作 |
| 6 | 云端生成与CPU加工 | 基准图及八动作制作、失败/未知结果处理、图集和manifest输出；平台校验后持久保存结果 |
| 7 | 后台预览、人工验收与Avatar发布 | 八动作可动态预览，未验收不可绑定；发布形成不可变版本；新制作不覆盖在用版本 |
| 8 | Voice配置与最小纯播报应用 | 官方音色与第三方TTS Relay配置、Voice版本、SPEAK_ONLY应用；通过调试Session完成真实试听、speaking动作与stop |
| 9 | 完整演示及故障验收 | 在真实服务完成形象制作和两类TTS路径；用可控故障验证幂等、重启、权限、停止和清理，形成M2记录及启动说明 |

第3～4步先完成骨架所需迁移，第5～8步追加业务迁移。48张表是完整第一版设计，阶段所需范围由真实依赖决定，不能为了少建表而省略已启用流程的额度、引用或恢复依据。

基础设施和服务的**日常启动依赖**：MySQL/Redis → Nacos就绪（若用外置库则先初始化Nacos自己的schema）→ RabbitMQ就绪 → ruoyi-system与ruoyi-session启动并完成各自迁移 → auth/gateway联通 → media API与Worker可用 → Vue后台。服务必须检查依赖就绪，不能把启动了进程等同健康。Nginx/Compose作为Linux部署入口验证，Windows本地允许IDE启动应用并连接同样的数据与云对象存储能力。

官方TTS与转接试听复用最小纯播报调试链路，不额外建立绕过Session鉴权和计额的试听通道。第三方厂商Key只在开发者示例后端，平台保存的是独立Relay访问凭证。

## 6. M2：形象与声音业务闭环验收

| 编号 | 操作/场景 | 必须观察到的结果 |
|---|---|---|
| M2-01 | 上传本人可使用的参考图 | 权利提示、真实文件类型/大小检查有效；文件进入云对象存储并取得fileId；账号B不能读取或使用账号A私有文件 |
| M2-02 | 创建制作任务并重复相同请求 | 返回同一任务及当前状态，只预占一次整套额度；任务离开页面后仍可查询 |
| M2-03 | 真实外部API制作一套全身资产 | 基准形象与固定八动作形成完整版本，程序完成透明加工、规范化、图集及正式manifest；平台不运行生成/抠图/插帧模型 |
| M2-04 | 检查生成文件及播放 | 哈希、尺寸、帧布局、锚点和动作集合符合接口规格；八动作逐一可预览，全身完整、动作可辨识、角色一致性与边缘由负责人验收 |
| M2-05 | 制作成功、人工验收、发布 | SUCCEEDED只表示产物完成；REVIEW不可绑定正式应用；验收发布后可引用；发布不再扣一次制作额度 |
| M2-06 | 新制作、在用版本及越权访问 | 新任务产生新候选版本，在用版本保持；跨账号查询/发布/引用拒绝；被引用资产删除受既定约束 |
| M2-07 | 明确失败、结果未知、重投及Worker重启 | 明确失败按契约恢复；未知保持待核对且不自动再次付费；过期Worker结果不能覆盖新执行；重复结果不重复扣额 |
| M2-08 | 文件上传/加工失败、结果保存中断 | 残留对象进入可恢复清理，产物未完整保存不能标成功或发布；任务、调用与额度事实可追踪 |
| M2-09 | 官方音色和开发者TTS音色 | 各至少一个真实音色可保存为Voice版本并试听；Relay能力测试与真实合成分开；厂商Key只在规定的一侧 |
| M2-10 | 选择已发布Avatar和Voice，输入文字 | 最小SPEAK_ONLY应用经登录后台创建DEBUG Session、取得S并播报；不调用LLM；文字不写AI历史 |
| M2-11 | 多段语音、暂停、缓冲、停止及迟到音频 | 按段号顺序播放；实际播放才驱动speaking；stop清空声音与动作队列，迟到音频不重播；重复stop安全 |
| M2-12 | 调试退出、Token过期、会话越权 | 原后台登录退出使相应调试授权失效；过期凭证/其他Session音频请求被拒绝；不能通过后台Token直接调用S运行时路由 |
| M2-13 | 合成成功后停止、合成失败与未知 | 合成事实与播放状态分开；官方已合成部分按规则结算、重复事件只结算一次，未知先核对；自定义TTS不扣官方TTS额度 |
| M2-14 | 页面刷新、服务重启和引用恢复 | 已发布Avatar、Voice和制作结果可重新加载；活跃轮次中断后不自动重播；固定版本及当前撤销限制保持 |
| M2-15 | 本轮结束、失败或停止后的临时数据 | 音频立即按契约变为不可访问并进入清理；失败清理有重试；正式资产保持可用，临时内容不混入长期业务日志 |

正式八动作保持 `idle/speaking/listening/thinking/nod/shake_head/wave/happy`。现有CLI的单动作六张PNG包需要显式转换为接口01的整套图集/manifest，不把本地预览通过直接当成正式包验收。当前6帧、512×768、6fps为接口初始规格；实测需要调整时同步版本契约与验收记录。

## 7. 验收方式与证据

- 真实成功路径至少覆盖一套完整八动作制作并发布、一个官方Voice和一个第三方Relay Voice的试听，以及同一Avatar切换Voice的纯播报演示。记录环境、模型/音色、请求ID、实际时间、可得用量和负责人视觉/试听结论。
- 重投、崩溃、上游结果未知等故障优先使用受控替身与故障注入验证，避免为了制造异常重复消耗真实付费请求。记录需区分真实调用和模拟故障；成功路径不能全部用替身代替。
- 本地手动验证保留；Java/Python/SDK行为检查与浏览器演示覆盖本稿验收项。本机完整服务组启动和本机浏览器至少各有一次实际记录，不以生成配置文件代替可用性证据。Compose仍作为后续Linux部署入口，但不再是本阶段验收门槛。
- 性能先记录耗时、请求数量、产物大小和内存/CPU观测，不虚构尚未经验证的响应速度承诺。0.4元/动作请求为此前实测参考；本阶段按实际调用和账单记录，未知成本标不可获取。
- 交付包括正式代码、迁移脚本、配置模板、启动说明、开源移植记录、正式样品包、验收记录与已知问题。每项状态使用未执行/通过/失败/阻塞及证据链接，不能仅用“代码完成”代替验收。
